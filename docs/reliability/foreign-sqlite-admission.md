# Existing SQLite database admission

A persisted `user_version` value by itself does not identify the owner or
schema of an existing SQLite file. On first open, Motionwright now
distinguishes a genuinely empty, unversioned database from a file containing
tables belonging to another application.

Before WAL-mode selection or `CREATE TABLE IF NOT EXISTS`, the storage layer
reads `sqlite_master` and checks the three mandatory legacy project-store
tables and their core columns: `projects`, `receipts`, and `events`.
An unrelated, incomplete, or falsely versioned database fails closed without
adding product tables or advancing `user_version`. The recognition is
rechecked under the SQLite IMMEDIATE writer transaction before schema DDL.
It checks **schema shape**, not an external ownership attestation or a
cryptographic signature.

An empty `user_version=0` database may be initialized. Databases with the
supported v1 common table layout may still upgrade transactionally to v2;
their project identity, serialized document and unrelated extension tables
are preserved. Versions greater than the compiled storage version continue to
be rejected, without editing future data. An existing file missing mandatory
tables is treated as incomplete rather than silently creating new tables
around its old contents.

The `foreign_sqlite_admission` integration regression covers a foreign
unversioned database, foreign supported-version databases, a misleading
`projects` table, and a source-equivalent v1 SQLite layout retaining actual
project identity. The v1 positive fixture is assembled from the historical
source table definitions; **it is not an original database generated by an
earlier compiled executable**, nor a signed installed-device acceptance test.

This source guard does not prevent an adversarial database intentionally
copying the full legitimate table shape, block concurrent file replacement
after path resolution, or prove all historical binary versions are compatible.
Those require separate owner-bound file handles, original historical
fixtures and installed validation. No external database is migrated for
testing and no user file is deleted.
