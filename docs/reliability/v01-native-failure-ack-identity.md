# v0.1 native AV: acknowledged job identity and terminal uncertainty

Scope: Motionwright v0.1's **CI-only native command failure classifier** and blocker [#49](https://github.com/seradotcom/motionwright/issues/49). This is a safe diagnostic correction, not a lifecycle fix or recovery of a failed job.

The canonical Motion Canvas workflow can acknowledge `driver.motion-canvas.render.start`, then fail later while polling the **same** native job. A typed error with `outcome_known=true` can describe the *enclosing CLI operation* or a read-only status failure; it does not establish the acknowledged render's terminal outcome. The failure report now conservatively retains `source_outcome=UNKNOWN` and `requires_original_job_owner_reconciliation=true` whenever the bounded journal includes an acknowledged start but no separately verified terminal native result. No new mutating job is created.

Append-only receipt logs may repeat `completed` stage rows for the same request ID. The classifier counts distinct start identities only within the same bounded envelope, scoped by the available creative project ID, generation and revision. Anonymous rows with no trustworthy ID form **at most one ambiguous evidence bucket**; they cannot prove an additional distinct start. The new `original_render_start_identity_ambiguous` boolean explicitly marks this limit. If both stdout and stderr contain typed receipt histories, the conservative maximum is used rather than summing duplicated streams. None of the request IDs, project IDs, job refs, original payloads, stderr or owner paths appears in the public report.

The prior failure classifier received a CLI process exit code but discarded it. A new closed-enum `cli_exit_category` distinguishes a normal nonzero exit, an invalid zero-exit response, an unobserved exit, a deadline, and a POSIX signal termination. `cli_signal_observed` includes only the bounded names SIGKILL, SIGTERM, SIGSEGV, SIGABRT, SIGBUS or OTHER_SIGNAL. A signal or missing exit makes the original native outcome UNKNOWN; `cli_signal_proves_oom_or_provider_loss` is always false. These describe the *Motionwright CLI process*, never upstream Driver Host causation, and do not include raw exit text.

Synthetic negative tests cover duplicate/anonymous requests, independent revision scopes, contradictory known and unknown results, malformed errors, cross-provider receipts, signal/deadline/normal exit distinctions and private-data redaction. They run in the dedicated v0.1 Native AV Failure Redaction GitHub Actions job alongside the existing source boundary and CLI regressions.

## Real native-render incident observations

A newer, source-bound `native-render-e2e` CI run on PR #223 completed with `malformed_native_failure_response`, `cli_exit_category=nonzero_exit` and `ci_native_motion_canvas_evidence=NOT_VERIFIED`. The sanitized public artifact contains no acknowledged original start or verified provider-generation loss. It therefore cannot determine whether the original work completed, and this is **not** proof of a Motionwright classifier defect, a Driver Host crash or a verified render. A separate native AV failure on an older PR showed provider `connected=1/disconnected=1`, still without root-cause proof.

In addition to the existing AV-master witness, the v0.1 native-render lane now starts the same read-only, 256 KiB-bounded owner-session Broker watcher **after obtaining a private owner session and before issuing the original render**. It finalizes the observer before intentional daemon teardown, even if the render command fails. The report stays inside ephemeral private CI evidence; public CI logs receive only fixed five-kind transition counts and an early-subscriber-exit flag. The public artifact uploader cannot access the raw watcher JSON. Synthetic watcher tests and exact-source CI verify these boundaries. The observations are explicitly non-exhaustive, cannot establish the causal failure or job terminal outcome, never grant native effects or restart an unknown job, and do not substitute for independently verified owner recovery.

This does **not** prove what happened to any original acknowledged job in failed run #49. The current upstream Driver Host lifetime issue remains open, as do GTK/glib security #89, explicit owner/Broker MLT-close authorization #91 and independent installed-product acceptance #126. Motionwright must remain `BLOCKED_PENDING_EXTERNAL_EVIDENCE` until those separate gates are satisfied. No v0.5 renderer logic, Semwright Native SDK source pin, original render retry, provider restart or destructive cleanup is changed.
